# x402 on Robinhood Chain

Tollex implements [x402](https://www.x402.org/) version 2 as both a resource server (its capabilities
answer with payment challenges) and a native facilitator (it verifies and settles the payments itself).

## Terms

| Field | Value |
| --- | --- |
| `x402Version` | `2` |
| `scheme` | `exact` |
| `network` | `eip155:4663` (Robinhood Chain mainnet) |
| `asset` | USDG `0x5fc5360D0400a0Fd4f2af552ADD042D716F1d168`, 6 decimals |
| `payTo` | treasury `0x2eB98e76db13287eD4AEE5F1C7f14a7e378966B7` |
| `amount` | per capability, in atomic USDG, stated in each challenge |
| Authorization | EIP-3009 `transferWithAuthorization`, signed by the payer |

## Challenge

An unpaid request to a paid capability, for example:

```bash
curl -i -X POST https://api.tollex.org/tools/chain_get_block \
  -H 'content-type: application/json' -d '{"block":"latest"}'
```

returns `402` with a `PAYMENT-REQUIRED` header (base64 JSON) containing the `accepts` list above, the
`resource`, and two extensions:

- `bazaar`: machine-readable description and input/output schema of the capability, for x402 discovery
  catalogues;
- `tollex-receipt`: how the receipt for this call will be signed and where to verify it.

Decode it with:

```bash
curl -s -D - -o /dev/null -X POST https://api.tollex.org/tools/chain_get_block \
  -H 'content-type: application/json' -d '{"block":"latest"}' \
  | grep -i '^payment-required:' | cut -d' ' -f2 | tr -d '\r' | jq -R '@base64d | fromjson'
```

If settlement gas has risen sharply since prices were set, the answer is instead
`503 {"error":"paid_calls_paused","charged":false}` with `Retry-After`. This is deliberate: Tollex does
not settle payments that would cost more in gas than the price covers.

## Payment and settlement

The client retries the request with a `PAYMENT-SIGNATURE` header carrying the signed authorization.
Tollex checks it against the challenge it issued, settles it on Robinhood Chain, runs the capability
once, and answers with the result and a `PAYMENT-RESPONSE` header (transaction hash, network, payer,
receipt).

- A payment that does not match the challenge (amount, asset, recipient, network, validity) is refused
  before the capability runs and nothing is charged.
- An authorization can settle at most once; the token contract records it as used.
- A price never changes after an authorization has been signed for it.

## Receipts

Every paid result carries an EIP-712 receipt (`Tollex Execution Receipt`, version 1) whose content hash
covers the request, the response, the pricing terms and the payment. The signing key is published at
`https://api.tollex.org/.well-known/tollex-receipt-keys` and can be checked independently.
